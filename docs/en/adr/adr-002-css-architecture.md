# ADR 002 — CSS Architecture for Documentation

**Author:** Giovani Fernandes  
**Date:** 2026-04-15  
**Status:** Accepted  

---

## Context

System documentation is rendered from Markdown files, converted to HTML by a renderer (CommonMark).

This scenario generates specific challenges:

* The generated HTML is not fully controlled
* Need for visual standardization across documents
* Risk of conflict with global application styles
* Need for scalability for future evolutions (themes, components, plugins)

Alternatives considered:

1. **Use of global application CSS**
   * Simple to implement
   * High risk of conflicts and visual inconsistency

2. **Use of Tailwind directly in HTML**
   * Limitation: Markdown does not generate utility classes
   * Makes fine styling control difficult

3. **CSS-in-JS**
   * Unnecessary complexity for the context
   * Increases coupling with the frontend

---

## Decision

Adopt a CSS architecture based on isolation and scoping, with the following guidelines:

* All documentation content must be contained within a `.docs-article` wrapper
* All CSS must be scoped with a `docs-` prefix
* Separation of styles by responsibility (layout, typography, components)
* Styling based on elements generated by Markdown
* Use of CSS Grid for layout
* Dark Mode support via `.dark`
* Mandatory responsiveness

## 🧱 General Layout

```css
.docs-layout {
  display: grid;
  grid-template-columns: 260px 1fr;
  min-height: 100vh;
}
```

## 📚 Sidebar (Navigation)

### HTML Structure

```html
<aside class="docs-sidebar">
  <nav class="docs-nav">
    <ul class="docs-nav-list">
      <li class="docs-nav-item">
        <a class="docs-nav-link active">Introduction</a>
      </li>

      <li class="docs-nav-group">
        <span class="docs-nav-group-title">Architecture</span>

        <ul>
          <li class="docs-nav-item">
            <a class="docs-nav-link">DDD</a>
          </li>
        </ul>
      </li>
    </ul>
  </nav>
</aside>
```

---

### Sidebar CSS

```css
.docs-sidebar {
  background: #0f172a;
  padding: 16px;
  overflow-y: auto;
}

.docs-nav-list {
  list-style: none;
  padding: 0;
}

.docs-nav-item {
  margin-bottom: 4px;
}

.docs-nav-link {
  display: block;
  padding: 8px 12px;
  border-radius: 6px;
  color: #cbd5f5;
  text-decoration: none;
}

.docs-nav-link:hover {
  background: #1e293b;
}

.docs-nav-link.active {
  background: #2563eb;
  color: #fff;
}
```

---

### Navigation Groups

```css
.docs-nav-group-title {
  font-size: 12px;
  text-transform: uppercase;
  color: #94a3b8;
  margin: 16px 0 8px;
}
```

## 📄 Article (Content)

### HTML Structure

```html
<main class="docs-content">
  <article class="docs-article">
    <h1>Title</h1>
    <p>Text...</p>
  </article>
</main>
```

---

### Container

```css
.docs-content {
  padding: 40px;
}

.docs-article {
  max-width: 900px;
  margin: 0 auto;
  line-height: 1.7;
}
```

---

### Granular Typography

```css
.docs-article h1 {
  font-size: 2rem;
  margin-bottom: 16px;
}

.docs-article h2 {
  font-size: 1.5rem;
  margin-top: 32px;
}

.docs-article h3 {

}

  margin-bottom: 16px;
}

  border-left: 4px solid #2563eb;
  padding-left: 16px;
  color: #475569;

### Code Blocks

  background: #0f172a;

    {{-- navigation tree --}}

    </article>
  </main>

```

---

## Consequences

### Pros

* Highly organized structure
* Easy evolution (components, themes, plugins)
* Clear and reusable navigation
* Low coupling with the backend

### Cons

* More files to manage
* Requires strict standardization
